## R2 — CSP tightened to the built-HTML policy: DONE

Root cause of the gap: `src-tauri/tauri.conf.json` carried a hand-written
policy looser than the `<meta http-equiv="Content-Security-Policy">` the app
already ships in `apps/desktop/index.html` — so the effective enforced policy
was the strict meta one, and the Tauri config granted unused slack
(`script-src 'unsafe-inline'`, dev-only `connect-src http://127.0.0.1:1420`,
unused `img-src blob:`, no `object-src`/`base-uri`/`frame-src`).

Change (`src-tauri/tauri.conf.json`, one line):

```text
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; connect-src 'self' ws://127.0.0.1:*;
object-src 'none'; base-uri 'none'; frame-src 'none'
```

Per-directive evidence (all verified, not assumed):

- `script-src 'self'` (dropped `'unsafe-inline'`): `npm run build` output
  `dist/index.html` contains exactly one `<script>` — an external module
  (`./assets/*.js`) — and zero inline `<script>`/`<style>` blocks. All Svelte
  `onclick`/`onchange` handlers compile to `addEventListener`, not inline
  attributes. The two `unsafe-inline`/`innerHTML` string hits in the bundle are
  Svelte-runtime template parsing (`<template>.innerHTML = …`, DOM API — not
  script execution; no `trusted-types` directive is set, so it is unaffected
  by `script-src`). No `eval(` / `new Function` anywhere in `apps/desktop/src`.
- `style-src` keeps `'unsafe-inline'` (scoped, documented): Svelte compiles
  component `<style>` to the external CSS bundle in prod, but runtime
  `style:*` directives and dev-mode HMR style injection need it; the shipped
  meta policy already required it, so keeping it changes nothing effective.
- `connect-src 'self' ws://127.0.0.1:*`: `'self'` covers same-origin dev fetch
  AND Tauri v2 IPC (same-origin intercepted `invoke` — proven because the
  identical meta tag already ships in dev + prod and `invoke`-driven flows
  work); the old `http://127.0.0.1:1420` entry was redundant with `'self'` in
  dev and dead in prod. `ws://127.0.0.1:*` is the Vite HMR socket (dev only).
- `img-src 'self' data:` (dropped `blob:`): no `createObjectURL`/`Blob(`/`blob:`
  usage anywhere in `apps/desktop/src`; screenshots use `canvas.toDataURL`
  (`data:`) + fs-plugin write. `data:` is required, `blob:` was dead.
- Added `object-src 'none'; base-uri 'none'; frame-src 'none'`: no
  `<object>`/`<embed>`, no `<base>` (Vite `base:'./'` uses relative URLs), no
  iframes — matches the already-shipped meta verbatim.

Proof nothing breaks: `cargo test -j2 --lib` 59/59 pass,
`cargo test -j2 --bin veyra-cli` 9/9 pass, `npm test` 30/30 pass,
`npm run check` (svelte-check) 0 errors 0 warnings, `npm run build` succeeds
and the rebuilt `dist/index.html` still carries the identical meta policy
(tauri.conf and meta are now byte-identical policies). Windowed launch still
needs a real display (unchanged, out of headless scope).

## R1 — fs capability scope: documented absence (no change, verified)

Root cause of the question: `src-tauri/capabilities/default.json` grants
`fs:allow-read-text-file`, `fs:allow-write-text-file`, `fs:allow-write-file`
with no static path `scope`. Verified this is load-bearing, not slack:

- The only fs-plugin call sites are `apps/desktop/src/tauri-api.ts`
  (`openJsonFile` → `readTextFile`, `saveJsonFile` → `writeTextFile`,
  `saveRendererScreenshot` → `writeFile`). All three take their path
  **exclusively** from an `open()`/`save()` dialog result (user gesture,
  JSON/PNG filters, 16 MiB size gates); no hardcoded, backend-derived, or
  concatenated paths reach the fs plugin (grep-verified, 2026-09-20).
- Legitimate dialog targets live outside any static scope: dataset-adjacent
  configs/reports on removable media, `/tmp`, shared lab mounts (`/data`),
  and user home subtrees. Any static `scope.allow` list (e.g. `$HOME/**`)
  would break the dialog-gated flows R1 is meant to protect, while adding no
  real restriction (the dialog already is the authorization).
- The privileged surface (dataset roots, backend staging) never touches the
  fs plugin: `commands.rs::validated_dataset_root` uses `std::fs::metadata`
  + `canonicalize` directly (metadata-only, directory check, no content
  read), and `supervisor.rs` spawns the backend via `std::process` — both
  unaffected by plugin capability scope by construction.

Verdict: keep the current grant; the authorization boundary is the
dialog-gated call-site discipline in `tauri-api.ts`, pinned here. If a future
audit wants defense-in-depth, the additive option is a `scope.deny` for
dot-directories — explicitly NOT added now (risk of breaking legitimate
dotfile-adjacent config flows, no headless way to prove otherwise).

New tests (7; `cargo test -j2 --lib supervisor::` 11/11 incl. 4 pre-existing):

| Test | Path proven |
|---|---|

| `stop_leaves_no_orphan_and_supervisor_restarts` (linux) | `/proc/<pid>` gone after `stop()`; supervisor accepts a fresh `start()` + `status` (stop-keeps-supervisor) |

| `response_packets_resolve_their_pending_sender` | `dispatch_packet` ok-response completes the exact waiter (no leak) |
| `error_responses_and_crashes_fail_pending_with_context` | error-response → `Response("boom")`; `fail_pending` (crash funnel) → `Process(_)`; telemetry queues as event, never resolves a waiter |
| `oversize_protocol_lengths_are_rejected` | metadata length `MAX_METADATA+1` rejected |

`stop-keeps-daemon` half outside this file: `runtime_shutdown` is a
session-level daemon command (`desktop_control/mod.rs::shutdown` sends
`"shutdown"` through the client; the host is joined only at app exit in
`lib.rs`), so the loopback daemon provably survives runtime stop — read-only
code, verified by reading, not modified. Pre-existing bin test
`runtime_stop_requests_a_runtime_stop_without_shutting_down_the_daemon`
(9/9 `veyra-cli` pass) pins the CLI side.

## Renderer pass (`MapCanvas.svelte`, static + headless-tested)

- Sampling disclosure (code review): caption shows packed counts as
  "`N points · M cells displayed`" (`App.svelte` map-coordinate); budgets are
  disclosed as *display-only* ("Display budgets are independent of map
  ingestion. Mapping processes all observations in each accepted frame.");
  mapper-domain totals (`ACTIVE CELLS`, `cells_by_level`) stay in telemetry
  cards with the `MEMORY_DOMAIN_NOTE` incomparability caption. Total-ingested
  vs rendered is therefore labeled at every site — no change needed.
- Real defect found + fixed: `update()` indexed the preallocated GPU buffers
  (`capacity = 100000`) with unclamped `meta.points.count`/`cells.count` —
  any frame exceeding capacity would throw inside the `$effect` and freeze
  updates. Unreachable today (budgets ≤ 100000, backend packs within budget)
  but one malformed frame from being a hard freeze. Fix: new pure helper
  `clampRenderCounts` (`dashboard.ts`, `RENDER_CAPACITY = 100000`) applied to
  both loops/draw-range/`mesh.count`; unit-tested headless (overflow clamps +
  `truncated`, `NaN`/`undefined` → 0, negatives → 0).
- Context loss (code review + minimal handler): previously no
  `webglcontextlost` listener — a GPU reset froze rendering silently. Added:
  `preventDefault()` (permits restore) + user-visible message (mapping
  continues in backend) + `webglcontextrestored` clears it. Full canvas
  re-creation on restore is NOT implemented — needs a real display to prove;
  recorded as a known gap below.
